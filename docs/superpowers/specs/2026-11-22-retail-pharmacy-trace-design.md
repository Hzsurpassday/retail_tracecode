# 零售药店追溯码系统 · 设计文档

- 日期：2026-11-22
- 状态：待整体验阅
- 范围：v1（核心闭环 + 退货；不含独立扫码页、不含拆零）
- 部署对象：单体药店，店内部署

## 0. 背景与需求汇总

为一家单体药店建设真实生产用的药品追溯码系统，对接阿里健康"码上放心"平台（零售药店权限包），实现追溯单据的自动采集、匹配、上传与状态闭环。

已澄清的需求事实：

1. 真实生产系统，非演示。凭证已齐备（AppKey/AppSecret 已申请并绑定授权，企业已入驻，ref_ent_id/ent_id 可得），可直接真实联调。
2. 店内已有 KSOA 收银/ERP，系统**直连其数据库只读取数**。销售时 POS 已扫追溯码并与单盒销售记录绑定；存在不需追溯码的商品。
3. 采购入库**优先用上游供应商出库单中的追溯码匹配本店入库单，免扫码**；无法完全匹配时人工补配介入后再上传。
4. 技术栈：.NET 8 ASP.NET Core + SQL Server，店内部署，浏览器访问。**业务库必须兼容 SQL Server 2008 R2**。
5. v1 范围：采购入库自动匹配上传、零售自动上传、处理状态跟踪、异常人工处理；退货纳入 v1（消费者退货、采购退货）。

平台硬规则（来自官方对接指南，具体限值与传参以合同验证为准）：

- AppKey/AppSecret 只能存在于服务端，严禁进入客户端代码、配置与日志。
- 网关 `https://eco.taobao.com/router/rest`，测试也用正式环境，不用沙箱。
- 上传为异步处理（约 5 秒延迟），上传成功 ≠ 处理成功，必须回查 billstatus。
- 单据号（bill_code）企业内唯一，重复上传报错；该报错只触发回查，不作为业务成功证据。
- 先上传入库单，才能查码信息/展开子码；追溯码规则：8 开头 20 位数字。
- 各接口独立限流（日/分钟/秒级），另有 AppKey 总调用量等共享限制。

核心接口（alibaba.alihealth.drugtrace.top.lsyd.*）：

| 接口 | 用途 |
| --- | --- |
| uploadinoutbill | 企业间出入库单据（102 采购入库、202 退货出库等） |
| uploadretail | 零售单据（含消费者退货 116，按现有 PRD） |
| query.billstatus | 上传后处理状态查询 |
| listupout / listupout.detail | 上游出库单列表 / 明细（带码） |
| query.upbillcode / query.upbilldetail | 按码查上游出库单号 / 按单号查本企业单据详情 |
| query.relation | 大包装码展开子码（须先入库） |
| query.codedetail | 按码查药品基础信息 |
| query.getbyrefentid / query.getentinfo / service.getenddate | 企业信息 / 服务期 |

## 1. 总体架构与组件边界

架构方案：单体应用 + 内置持久任务引擎（方案 A，已批准）。

```
浏览器(React) ── HTTP ──> Web API 层 ──┐
                                      ▼
                              应用业务层（唯一规则实现）
                    匹配 / 资格校验 / 码占用冻结 / 任务创建
                                      │
        ┌──────────────┬──────────────┼─────────────────┐
   KSOA适配器      独立业务库      持久任务引擎        码上放心Client
  (只读KSOA库)   (SQL Server)   (原子认领+租约)      (TOP+三级限流)
```

### 1.1 应用业务层

匹配、资格校验、追溯码占用冻结、任务创建的**唯一实现处**。Web API 的人工操作与后台管道走同一套规则，杜绝两套逻辑。

### 1.2 KSOA 适配器

- 按已知真实结构开发：销售 `salemast/salemxls`、采购入库 `jh_rkhz/jh_rkmx` 及已确认字段（字段明细以适配契约文档为准）。
- 稳定行键、单位换算必须对真实数据验证。配置化仅用于适配现场差异，**不承诺"一切变化只改配置"**。
- 对 KSOA 库只读、独立低权限账号。
- 尚未取证的适配能力在界面显示"未接入/未验证"并**禁用对应发送**，不用演示成功替代。

### 1.3 独立业务库

- 独立 database，允许与 KSOA 位于同一数据库服务器实例。
- **兼容 SQL Server 2008 R2**：数据访问采用 **Dapper + 手写 T-SQL**（弃用 EF Core 8，其 SQL Server 支持基线高于 2008 R2）；分页、认领等全部语句按 2008 R2 语法在真实实例上验证。
- 业务库与 KSOA 使用不同权限的连接账号。

### 1.4 持久任务引擎

- 所有后台作业落库为持久任务；`UPDATE ... WITH (UPDLOCK, READPAST)` 原子认领 + 租约超时回收；进程重启不丢不重。
- 单部署单元**不代表后台任务可依赖进程内存**：三条以上管道共用持久任务、原子认领、租约和状态机。
- 上传超时或发送后崩溃 → 单据进"受理未知"，先回查再决策，**禁止直接重新上传**。
- 作业清单：POS 来源同步、上游出库单下载、主数据匹配、码信息解析与业务核验、入库匹配上传、零售上传、状态回查、发送恢复、日对账。

### 1.5 码上放心 Client

TOP 协议签名与公共参数、网关调用、按接口独立限流 + 共享预算。**模拟与真实硬隔离**：任务带环境标记（Live/Mock），分队列、分回执、分配置，**码占用与业务状态推进也按环境隔离**；Mock 成功不推进真实单据/码状态；模式切换只影响新任务，存量 Mock 任务永不发往正式平台。

### 1.6 宿主与持续运行

- 首选 **Windows 服务自宿主（Kestrel + UseWindowsService）**，开机自启、崩溃自动恢复，不依赖 IIS 空闲回收策略。
- IIS 与 Windows 服务不视为同等运行条件：若客户坚持 IIS，必须配置 AlwaysRunning + 禁用空闲超时，并单独验收持续运行能力。
- 验收项包含连续运行与重启后任务自动恢复（见第 5 节）。

### 1.7 前端

React（Vite 构建后置于 wwwroot，随 .NET 一起发布，仍是一个部署单元）。页面能力不省略、导航可合并：工作台、商品/供应商映射、上游单、入库关联、POS 销售、退货、码台账、上报对账、**人工补配与异常处理**（本期不做独立扫码页）、设置、审计。

## 2. 数据模型、状态机与事务边界

### 2.1 来源镜像与稳定行键

- 镜像表 `pos_sale/pos_sale_item`、`pos_purchase/pos_purchase_item`：保存**不可变版本**（源行变更追加新版本，不覆盖）、**完整行摘要**（哈希，变更检测与完整性校验）、**完整性状态**（正常/缺键/摘要冲突）。
- "源单号+明细行号"仅为**候选键**：销售 `plh` 为空的记录无法构成稳定键，**不得静默过滤丢行、不得临时生成行号**，一律进入**接入异常队列**。
- 缺键的人工解决路径：取得可靠来源字段 → 验证稳定组合键 → **更新适配契约**；未解决前保留接入异常，无"点击放行"。
- 同步水位（checkpoint）与镜像数据**同事务提交（T1）**，检查点永不领先于已落库数据。

### 2.2 主数据映射

- `product_map`：KSOA 商品 ↔ 平台药品。**追溯分类（UNKNOWN/REQUIRED/EXEMPT）与映射状态（待匹配/候选/冲突/已确认）分开管理**：五项匹配不满足时进入待匹配/候选/冲突，**不得把已明确需追溯的商品改回 UNKNOWN**。
- 自动确认必须同时满足：**批准文号、生产企业身份、剂型、含量、包装规格**五项一致，且**双向唯一**；缺一不可。
- 含**人工锁定标记、映射版本号、历史证据**（历次确认依据留痕）。EXEMPT（无码商品）须登记依据，不允许默认豁免。
- `supplier_map`：KSOA 供应商 ↔ ref_ent_id/ent_id，同样带版本与证据。

### 2.3 入库分配（行级）

- 分配表 `inbound_allocation`：**本地入库行 ↔ 上游出库明细 ↔ 实际码集合**三元关联，保存**包装层级与单位换算比例及证据**、分配数量、占用状态。
- 支持**分批入库**与**一单关联多张上游单**；禁止只关联单头或仅比较合计数量。
- **本期不支持拆零**：不凭比例生成子码，不分摊无法识别的部分包装。

### 2.4 码台账 + 不可变事件流水

- `code_ledger`：每码当前状态与占用单据 ID（现状快照）。
- `code_event`：**不可变流水**，记录入库/销售/退货事件及**前序事件关系**（销售→原入库、退货→原销售/原入库），历史永不覆盖。

### 2.5 退货规则

- **消费者退货：`uploadretail / 116`**（按现有 PRD）；**采购退货：`uploadinoutbill / 202`**。不得把消费者退货记成 103。具体平台传参以合同/接口文档验证为准，开发前用平台测试工具逐项核实。
- 前序关系区分：**消费者退货关联原销售；采购退货关联原入库或真实库存来源证据**（不要求采购退货关联原销售）。
- 两类退货首次上报均按既定**人工确认规则**执行；**负数行不自动上传**，未满足关系校验的进人工补配。

### 2.6 状态存储与转换表

**分维度保存状态**：来源完整性、匹配、核验、依赖、上传状态各自独立字段，不合并为单一"七态"。

上传状态维度取值：已排队、发送中、已受理、处理中、全部成功、部分成功、结果无法判定、确定失败、受理未知。

转换表（当前状态 + 事件 + 条件 → 下一状态）：

| 当前状态 | 事件 | 条件 | 下一状态 |
| --- | --- | --- | --- |
| 已排队 | 认领成功 | 租约+fencing token 有效，send_attempt 已持久化 | 发送中 |
| 发送中 | 收到受理回执 | response_success=true，token 校验通过 | 已受理 |
| 发送中 | 传输超时/连接中断 | 请求可能已发出 | 受理未知 |
| 发送中 | 租约丢失/进程崩溃 | 恢复作业发现 send_attempt | 受理未知 |
| 发送中 | 明确业务拒绝 | 平台返回确定失败，token 有效 | 确定失败 |
| 发送中 | 重复单据号报错 | 仅触发回查 | 受理未知 |
| 已受理/处理中 | 回查：处理中 | — | 处理中 |
| 已受理/处理中 | 回查：全部码成功 | 逐码结果齐全且全 SUCCESS | 全部成功 |
| 已受理/处理中 | 回查：部分码失败 | 保存逐码结果 | 部分成功 |
| 处理中 | 回查无法判定 | 一致性延迟窗口内/证据不足 | 结果无法判定（继续回查或转人工） |
| 受理未知 | 回查确认已受理 | 平台记录证据 | 已受理/处理中 |
| 受理未知 | 回查确认未受理 | 满足未受理证据条件（延迟窗口+合同证据） | 已排队 |
| 受理未知 | 仍无法确定 | — | 保持阻断，转人工核对 |
| 确定失败 | 受控补救 | 合同支持路径+人工审批 | 创建补救任务（原单状态不变） |

- **逐码结果必须包含 UNKNOWN**：未返回失败的码不得直接视为成功。
- **部分成功**保存逐码结果，仅对失败码走受控补救，**禁止整单重新排队**；UNKNOWN 码继续核对，未查明前禁止重新发送。
- **受理未知重新排队条件（收紧）**：一次查询无记录 ≠ 未受理；须结合平台一致性延迟窗口与合同证据综合判断，仍无法确定 → 转人工核对，不自动重传。
- **码占用释放**：**终态失败不自动释放**。释放前置条件：确认平台未形成有效流转、无成功子单/成功码，且经**受控事务**执行。受理未知、处理中、部分成功一律不得自动释放；**本地作废不能抵消平台已发生流水**。
- 非法状态转换拒绝并告警。

### 2.7 任务引擎与 fencing

- `sync_task`：持久任务，环境标记（Live/Mock）、租约到期时间、**fencing token**（每次认领递增）。
- 租约过期可重新认领**处理权**，但**不自动恢复"上传动作"**：发送阶段失租的任务，新认领者必须先回查受理结果再决策。
- 任何结果写回须校验**当前租约持有者 + fencing token**，旧 Worker 的迟到写回一律拒绝。
- **旧 Worker 迟到回执可留证但不得推进状态**：token 失效后拒绝更新任务、码占用和业务状态；已取得的回执追加到只读尝试证据中，由当前持有者核对，不丢失受理信息。

### 2.8 幂等锚点

- `bill_code` 按 **门店主体 + 来源系统 + 业务事件 + 分片** 确定性生成，**生成即持久保存**，不依赖运行时重算。
- 平台"重复单据号"报错**只触发回查**，不作为业务成功证据，也不假设所有重放安全收敛。

### 2.9 事务边界

| # | 同事务提交内容 | 事务外 |
| --- | --- | --- |
| T1 | 来源镜像行 + 同步检查点 | 对 KSOA 的读取 |
| T2 | 资格检查结论 + 码占用冻结 + 不可变上传载荷 + 稳定单号 + 任务入队 | HTTP 上传请求 |
| T3 | 回执追加 + 合法状态转换 + 逐码结果更新 | 回查 HTTP 请求 |

- **发送前持久化边界**：T2 是创建任务；每次实际 HTTP 上传前，还须**短事务记录发送尝试（send_attempt）、当前租约及 token，并将任务推进"发送中"**。否则发送后崩溃无法判断请求是否已发出。
- 回执表保留**每一次上传与回查尝试**（含超时/无回执的尝试记录），不假设"一次上传必有受理回执"。

## 3. 后台作业与码上放心 Client

### 3.1 作业清单（全部为持久任务，租约认领）

| 作业 | 触发 | 职责 |
| --- | --- | --- |
| POS 来源同步 | 周期（分钟级） | 增量抽取 + **持久检查点、重叠回扫、停机缺口补拉、头明细完整性复查**；缺键行进接入异常 |
| 上游出库单下载 | 周期 | listupout / listupout.detail 增量下载；**列表与详情分别记录分页进度，详情未全部成功不能标为完整** |
| 主数据匹配 | 事件+周期 | 五项一致＋双向唯一→自动确认；否则候选/冲突进人工补配 |
| 码信息解析与业务核验 | 事件 | **零售上传前置核验**：绑定来源版本、实际码集合和规则版本；商品分类明确、所有应追溯码核验通过、入库依赖满足后才进入零售发送队列；超时等待、UNKNOWN 阻断；负数退货须满足首次人工确认规则 |
| 入库匹配上传 | 事件 | 行级分配→资格校验→码冻结→不可变载荷→T2 入队 |
| 零售上传 | 事件 | 核验通过后组装 uploadretail；EXEMPT 按依据跳过 |
| 状态回查 | 周期+退避 | billstatus 轮询；逐码结果落库（含 UNKNOWN） |
| 发送恢复 | 周期 | 扫描"发送中"且租约过期的任务→置受理未知→先回查再决策 |
| 日对账 | 每日定时 | POS 单 vs 本地已上报 vs 平台状态三方比对；**核对上游下载完整性，不能只比较已进入本地的数据**；差异报告进工作台 |

### 3.2 单次上传的发送协议（崩溃可判定）

```
认领任务(原子, fencing token+1)
  → 短事务：写 send_attempt(第N次尝试, 租约, token, 时间) + 任务置"发送中"
  → 事务外：HTTP 上传
  → T3：校验租约持有者+token → 追加回执 + 合法状态转换 + 逐码结果
```

- 短事务先于 HTTP 落库，保证任何发送后崩溃都能从 send_attempt 判定"请求可能已发出"，恢复作业一律走受理未知→回查路径。
- 旧 Worker 迟到写回因 token 不符被拒绝（回执留证，见 2.7）。

### 3.3 码上放心 Client

- **协议**：TOP 公共参数+签名，网关 `eco.taobao.com/router/rest`，正式环境直连；**签名算法与接口入参以实际合同验证结果为准**（开发前用平台测试工具核实，留存证据）。
- **限流与共享预算**：按接口独立的日配额、每分钟、每秒（ref_ent_id 维度）限制之外，还须处理 **AppKey 总调用量及平台返回的其他限制**；多个 Worker 共享调用预算；**上传、核验、回查均计入对应预算**；遵守平台明确等待时间；计数器**持久化**（重启不清零），超限任务改期而非硬撞。
- **错误处置按调用类型区分**：
  - 上传请求可能已发出时，超时 → 受理未知流程；
  - **查询请求超时只是查询待重试，不改变原单据受理状态**；
  - **客户端及 HTTP 中间件禁止透明重试上传 POST**；
  - `FAIL_BIZ_AUTH_ERROR` → **按接口、主体和凭证范围暂停**相关管道+告警，避免无关任务一并停掉；
  - 重复单据号 → 只触发回查；
  - 限流错误 → 退避改期；
  - 业务校验失败 → 确定失败/部分成功，按逐码结果受控处理。
- **Live/Mock 硬隔离**：任务、回执、配置分队列分存储；**码占用与业务状态推进按环境隔离**——Mock 有独立占用空间与状态副本，Mock 成功绝不推进真实单据/码状态；模式切换只影响新建任务，存量 Mock 任务永不发往正式平台。
- **凭证安全**：AppKey/AppSecret 加密存 `app_setting`（Windows DPAPI），仅服务端读取，前端与日志永不出现明文。**明确 DPAPI 保护作用域与服务运行账号**；换机/恢复备份时提供凭证恢复或重新录入方案；**密文不可解密时停止对应调用并告警，禁止退回默认凭据**。

### 3.4 可测试性

- Client 与 KSOA 适配器接口化，单元测试用 Fake 替代；状态机转换表、限流预算、认领/fencing、发送恢复逻辑全部有独立单测。
- **数据库集成与故障注入为必做项**：单测不足以证明认领原子性和事务正确，必须在真实 SQL Server 2008 R2 上用独立连接验证并发认领、过期租约、旧 token 写回，以及发送前后、回执落库前崩溃的恢复行为（见第 5 节）。
- 真实平台合同验证与联调限定为**经授权的真实业务**，不得提交虚构交易。

## 4. Web 页面与人工工作流

导航可合并，能力不省略。

### 4.1 工作台

管道健康（各作业最近运行/积压）、待办队列计数、告警（授权暂停、租约恢复事件、对账差异、核验阻断）、今日上传与成功率。**页面持续显示当前环境（Live/Mock）**。

### 4.2 人工补配与异常处理（统一队列视图，按类型分页签）

- **接入异常**：缺稳定键行；处理动作必须是"取得可靠来源字段→验证稳定组合键→更新适配契约"，未解决前保留异常，无"点击放行"。
- **映射候选/冲突**：五项证据并排展示＋双向唯一检查结果；**人工确认须先解决身份冲突**；确认/锁定留版本与证据。
- **入库未匹配**：本地入库行↔上游明细人工关联，登记包装层级换算比例及证据；**须满足批号、数量、真实码集合等强冲突约束**；无法识别的部分包装不分配、不生成子码。
- **核验阻断**：UNKNOWN 码、入库依赖未满足的展示与处置入口。
- **受理未知人工核对**：人工**提交核对证据，由后端校验证据、版本及合法转换**；确认已受理只能进入已受理/处理中，**全部成功仍需平台最终结果**；无法确定时继续阻断；重新排队须满足已约定的未受理证据条件。人工不能直接"判成功"。
- **部分成功补救**：区分"**失败码补救**"与"**UNKNOWN 继续核对**"。UNKNOWN 可能已成功，未查明前禁止重新发送；失败码只能采用**平台合同支持的补救路径**，不默认新建补传单。
- **占用释放审批**：**独立权限**。人工勾选声明不构成充分证据；审批时展示平台核对结果、成功子单/码检查及受影响业务；**执行时再次检查版本、依赖和占用**，防止审批期间状态变化；经受控事务执行。
- 所有人工提交**携带版本和幂等键，过期版本拒绝**；确认补配前明确提示"**符合资格后将自动上传**"；所有动作完成后可查看处理结果。

### 4.3 商品/供应商映射

追溯分类与映射状态分开管理；EXEMPT 须登记依据；历史版本可追溯。

### 4.4 上游单 / 入库关联 / POS 销售 / 退货

单据浏览＋钻取到码级。退货页区分两类前序关系（消费者退货↔原销售；采购退货↔原入库或库存来源证据），首次上报一律走人工确认，负数行不自动上传。

### 4.5 码台账

每码现状＋不可变事件流水（入库→销售→退货前序链）、占用单据、环境标记。

### 4.6 上报对账

日对账报告（POS vs 本地 vs 平台三方），含上游下载完整性核对；差异项可钻取、可转人工待办。

### 4.7 设置

凭证管理（DPAPI 保护、显示服务运行账号与作用域；换机/恢复备份重新录入向导；密文不可解密→停调用+告警，无默认凭据兜底）、KSOA 连接与适配契约版本、Live/Mock 切换（明示隔离语义，切换仅影响新任务）、限流预算配置与用量。

### 4.8 审计

所有人工操作、状态转换、发送尝试、租约回收事件只读留痕，可筛选导出。

### 4.9 权限与统计口径

- 两个角色（管理员/操作员）作为模板，**权限项细分**：映射确认、分类变更、入库补配、退货确认、安全重试、释放审批、凭证管理、审计导出等独立权限；操作员不因具有"确认"权限而获得所有敏感动作权限；**后端逐请求校验**。
- **Live/Mock 的列表、待办、成功率和导出分别统计**；"成功率"使用**最终全部成功**口径，部分成功、处理中、受理未知单列，不混入成功数。

## 5. 部署运维与测试验收

### 5.1 部署形态

- **单一发布单元**：.NET 8 自包含发布 + React 构建产物进 wwwroot；Windows 服务自宿主（UseWindowsService + Kestrel），开机自启，配置服务失败自动恢复。店内局域网浏览器访问。
- **数据库**：独立 database（可与 KSOA 同实例）；KSOA 只读账号与业务库专属账号分离。
- **数据库升级使用独立部署权限**：运行账号不具有建库、改表权限；升级前备份并暂停相关作业；版本化幂等 SQL 脚本记录**版本、校验摘要及执行结果**；**失败须停止启动或进入维护模式，不能部分升级后继续上传**。全部语法在真实 SQL Server 2008 R2 上验证。
- **连接安全（上线门禁）**：验证实际驱动、操作系统、SQL Server 补丁及 TLS 组合（含 2008 R2 未打 TLS 1.2 补丁时的兼容处理）；**禁止失败后静默降级连接**。
- **局域网访问安全（上线门禁）**：Kestrel 的 HTTPS、证书、监听范围、防火墙及服务账号权限须有明确配置和验收证据。
- **凭证**：DPAPI 保护，作用域与服务运行账号绑定；换机/恢复备份→重新录入向导；密文不可解密→停调用+告警。
- **备份与恢复**：业务库定期备份（含任务/回执/码流水）。**恢复后不能立即自动发送**：必须先暂停 Live 发送，核对缺口期间的平台记录、稳定单号、码占用与任务状态，修复后**经授权恢复发送**；租约恢复作业不能代替这一步。恢复演练纳入验收。

### 5.3 验收标准

措辞区分**本地保障**与**平台事实**：故障注入应证明——同一业务意图只创建一次、未知受理不盲目重发、迟到结果不能推进状态、最终平台流水与本地记录可对账。**不能仅凭"平台拒绝重复号"宣称实现分布式恰好一次。**

1. 采购入库：上游单匹配→免扫码上传→billstatus 全部成功；未匹配行走人工补配（版本/幂等键/强冲突校验生效）后自动上传。
2. 零售：核验作业通过才入发送队列；UNKNOWN/依赖未满足被阻断；EXEMPT 按依据跳过。
3. 退货：两类前序关系校验＋首次人工确认；负数行不自动上传。
4. 崩溃恢复：故障注入下满足上述本地保障四条；受理未知全部走回查；旧 Worker 写回被拒。
5. 限流：共享预算生效，超限改期不硬撞，遵守平台等待时间。
6. 对账：三方比对＋上游下载完整性核对，差异可钻取转待办。
7. 持续运行：连续运行 ≥7 天作为**试运行目标**；通过标准明确为：积压清空或在约定阈值内、受理未知全部处置、异常队列处置完成、日对账连续通过；重启/断网/数据库瞬断后自动恢复。
8. 隔离与安全：Mock 成功不推进 Live 任何状态；权限逐请求校验；凭证不落前端/日志；未验证能力禁用发送；连接与局域网安全门禁有验收证据。
9. 备份恢复：恢复后暂停 Live 发送→缺口核对→授权恢复的流程演练通过。

## 附录 C：术语

- **受理未知**：上传请求可能已发出但结果不明的状态；只允许先回查再决策。
- **fencing token**：任务每次认领递增的令牌，拒绝旧 Worker 迟到写回。
- **占用冻结**：码分配到单据后禁止再分配，直至受控释放。
- **T1/T2/T3**：三条事务边界（来源镜像+检查点 / 资格+冻结+载荷+入队 / 回执+状态+逐码结果）。
- **Live/Mock**：真实平台环境与模拟环境，任务、回执、配置、码占用、业务状态、统计全隔离。
